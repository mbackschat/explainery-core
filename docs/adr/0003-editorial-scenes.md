# 0003 Editorial scenes and persistent authoring focus

A person works on a narrative scene, which can require several executable HTML compositions. Treating every composition as a scene makes selection and iteration too granular. This decision extends the original [architecture contract](0001-explainery-architecture.md); the [scene authoring guide](../authoring.md#concepts) defines the terms.

`story.scenes` accepts explicit `{ id, title, compositions }` groups, with one grouping level. Existing flat composition entries remain one-composition scenes. Composition IDs, file paths, `defineScene`, and the keys of `timing.scenes` retain their existing meaning. Scene ranges are derived from their compositions; no second timing authority is introduced. Narration and assembly flatten groups in order, while explainer pages present editorial scenes.

Scene preview and rendering derive a local project that keeps shared layers and clips continuous audio. Each command refreshes copies of authored runtime files. HyperFrames checks resolved file paths against the project root, so linking compositions from the derived project back to their source is rejected. Dependencies retain the supported `node_modules` link. The derivative is disposable, ignored, and never an editing destination. Consecutive scene selections support transition review without rendering the film. Overlaps with omitted neighbors are allowed: isolated review retains the selected compositions' complete range, while a transition review includes both scenes.

The active authoring scope is a local film selection persisted by `focus`, independent of the story and git. Conversational scene selection sets it; later edits, previews, and renders use it until another scene or the whole film is selected. Commands announce scope and offer explicit one-command overrides. Validation, timing generation, assembly, and page export remain full-project operations. No separately encoded scene cache or new shot entity is introduced.
